pa-fhir-poc

"pa" as in prior authorization — an agentic-workflow POC applied to policy digitization

A proof of concept for agentic AI workflows applied to a real regulatory problem. A local LLM does the reading — pulling coverage requirements out of payer policy PDFs — but it works inside a structure that never takes its word for anything: extraction is quarantined behind snapshots, its output lands in a Neo4j graph as facts a reviewer can inspect, and a durable Temporal workflow blocks until a named human approves. Only then are Da Vinci CRD/DTR FHIR artifacts projected, and nothing is called conformant until the official HL7 validator agrees.

Medicare. Two real Local Coverage Determinations — glucose monitors (L33822) and PAP devices for sleep apnea (L33718) — go in as LCD + policy-article PDF pairs and come out as a CRD coverage card, a DTR Questionnaire, and a PlanDefinition. Each Questionnaire passes the validator against the Da Vinci DTR profile with zero errors and zero warnings (conformance reports); the second LCD went in as a fixtures-only change — no new code.

Commercial payers. Cigna's surgical sleep-apnea policy is a structurally different document: no companion article, and criteria organized as CPT/HCPCS code tables whose headings are the coverage stances. A per-publisher dialect seam, sniffed from the document itself, absorbs the format difference; everything downstream runs unchanged, and denial reasons come out deterministically — no LLM involved. One honest finding: a policy that states no documentation requirements projects no Questionnaire at all (the DTR profile requires at least one item) — the pipeline won't fabricate one to look complete.

The CMS Interoperability and Prior Authorization Final Rule (CMS-0057-F) puts a deadline on this: impacted payers must stand up prior-authorization APIs by January 1, 2027, and each starts from the same place — coverage policy written as prose. Medicare contractors and commercial plans alike face it; that's the pair demonstrated here. The projected artifacts for all three policies are committed at docs/examples.

fhir-zod-gen

v0.1, early — seeking contributors

This one exists because of a gap I kept hitting while building pa-fhir-poc: the only serious FHIR validator is a Java tool, so checking an artifact meant spinning up Docker every time. Meanwhile most new health-tech code — SMART on FHIR apps, Node backends, AI agents — is written in TypeScript, which has nothing equivalent. fhir-zod-gen closes that gap by generating Zod schemas from FHIR profiles, so validation becomes a plain import.

You name a published IG package — npx fhir-zod-gen hl7.fhir.us.core#6.1.0 — and it resolves that package and its dependencies, then writes one readable schema file per profile. Call .parse() on incoming data to validate it, and the TypeScript type comes free from the same declaration. That's useful anywhere FHIR crosses a boundary — checking an API response, guarding what an LLM produced, validating before you send. It builds on the FHIR Schema format, aiming to be the TypeScript sibling of Health Samurai's Python generator. It covers cardinality, nested elements, required bindings, choice types, slice cardinality, primitive regexes and the mechanically-translatable FHIRPath invariants — and the generated schemas accept all 441 published conformance examples across the four packages it is tested against.
